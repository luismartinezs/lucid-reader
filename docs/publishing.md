# Publishing Lucid Reader: the steps only you can do

This document lists what is left after the code work, in the order to do it.
Everything here needs either an account you own (Microsoft, Stripe, Cloudflare),
a running VS Code, or a `git push`, which is why none of it is done already.

Two repositories are involved: `~/dev/lucid-reader`, the extension, and
`~/dev/shop-appforgelabs-v2`, the shop that gives it away and takes donations.
Both are edited and neither is committed.

---

## What is already done

**In `~/dev/lucid-reader`.** The manifest carries a publisher, an icon
(`media/icon.png`, 128x128), the repository, homepage, issue tracker, gallery
banner, and a `sponsor` link to the shop page. Version is `0.2.0` and the
changelog entry for it is written. The README opens with a screenshot and has an
Install section. Three screenshots are generated by `bun run shots`, which
renders a document through the real parser and the real webview runtime in
headless Chrome. `npm run package` produces a clean 13-file, 58.81 KB vsix with
no warnings. One rendering defect was fixed on the way: smart quotes never
curled double quotes, because the substitution ran after HTML escaping and
looked for `"` in text where every double quote was already `&quot;`.

**In `~/dev/shop-appforgelabs-v2`.** A product can now declare
`pricing: 'free'` or `pricing: 'donation'`. Free products are claimed through
`POST /api/shop/claim`, which writes a zero-amount transaction, grants
ownership, and emits `PAYMENT_SUCCEEDED` so the existing confirmation email
goes out. Donations are an ordinary Stripe checkout against a Price created
with `custom_unit_amount`, so the payer types the amount and nothing downstream
changes. The catalog has `lucid-reader` (free, category `tools`) and
`lucid-reader-donation` ($5 preset, hidden from listings), a cover image, and a
product page with two buttons. Backend and frontend type-check, the frontend
builds, lint is clean, and the backend suite is at 160 passing with 1
pre-existing failure that is unrelated (see the last section).

## Part 1: the VS Code Marketplace

### 1. Register the publisher

1. Sign in at <https://dev.azure.com> with the Microsoft account you want to own
   this, and create an organization if you have none.
2. Create the publisher at
   <https://marketplace.visualstudio.com/manage/createpublisher>.

**The publisher ID is permanent and becomes half of the extension's identity.**
`package.json` currently says `"publisher": "appforgelabs"`, which is my
assumption, not your decision. If you register a different ID, change it in
three places: `package.json`, the `ext install appforgelabs.lucid-reader` line
in `README.md`, and the sponsor URL if the shop domain differs.

### 2. Create the token

At <https://dev.azure.com>, open User settings, then Personal access tokens,
then New Token. Two settings matter and both are easy to get wrong:

1. **Organization** must be "All accessible organizations", not the single
   organization the dropdown defaults to.
2. **Scopes** must be Custom defined, then Marketplace, then Manage.

Copy the token now, because the page never shows it again. It expires after at
most 1 year, and a publish that fails with a 401 later almost always means the
token expired rather than that the manifest is wrong.

### 3. Try the build in a real editor

```bash
cd ~/dev/lucid-reader
npm run install-local          # builds, packages, installs the vsix
```

Then run "Developer: Reload Window" in VS Code, because installing does not
affect the window that is already running, and check four things:

1. `Ctrl+K R` on any `.md` file opens the reader.
2. A paragraph containing "quoted text" now shows curly quotes. This is the
   parser fix, and it is the only behaviour change in `0.2.0`.
3. `T` opens the theme picker and arrow keys preview palettes.
4. The Wrap button in a fenced code block's caption toggles wrapping.

This is the step I could not do for you: nothing here can drive a real VS Code
window.

### 4. Publish

```bash
npx @vscode/vsce login appforgelabs     # paste the token
npm run publish                          # compiles, then vsce publish
```

The upload runs a malware scan and the listing is usually live within a few
minutes at
`https://marketplace.visualstudio.com/items?itemName=appforgelabs.lucid-reader`.

**There is a second route if you prefer pushing tags.** `.github/workflows/publish.yml`
publishes on any tag matching `v*`. Add the token as a repository secret named
`VSCE_PAT` (Settings, Secrets and variables, Actions), then release with
`npm version minor && git push --follow-tags`.

### 5. Commit and push

I did not commit anything in either repository. In `~/dev/lucid-reader` the
changed and new files are `package.json`, `README.md`, `CHANGELOG.md`,
`.vscodeignore`, `src/markdown.ts`, `media/icon.png`, `scripts/icon.html`,
`scripts/screenshots.mjs`, `docs/screenshot-prose.md`, `docs/screenshots/*.png`,
`docs/publishing.md`, and `.github/workflows/publish.yml`.

Push before you publish if you use the tag route, and push anyway if you publish
by hand, because the README on the Marketplace loads its screenshots from
`raw.githubusercontent.com` and those files have to exist on `main` first.

### 6. Optional: Open VSX

Cursor, VSCodium and Windsurf do not use the Microsoft Marketplace. Publishing
there as well takes an account at <https://open-vsx.org> and two commands:

```bash
npx ovsx create-namespace appforgelabs -p <open-vsx-token>
npx ovsx publish lucid-reader.vsix -p <open-vsx-token>
```

## Part 2: the shop

**Read this before you push to `main`.** The shop deploys itself on every push
to `main` (`.github/workflows/deploy.yml`), and the backend refuses to start
when Stripe is configured but a non-free product has no price ID. The donation
product is a non-free product. If you push before setting
`STRIPE_LUCID_READER_DONATION_PRICE_ID` on the server, the API will not come
back up. Do steps 1 and 2 first.

### 1. Create the donation price in Stripe

The seed script now understands donations and takes product keys, so it will not
re-create the Stripe objects of anything you already sell:

```bash
cd ~/dev/shop-appforgelabs-v2
bun run seed:stripe lucid-reader-donation
```

It prints a line to paste into `apps/backend/.env`:

```
STRIPE_LUCID_READER_DONATION_PRICE_ID=price_...
```

The Price it creates has `custom_unit_amount` enabled, presets $5 (500 cents),
and sets a $1 minimum (100 cents), because Stripe rejects card charges below 50
cents in USD.

Run it once with your sandbox key for local testing and once with the live key
for production, since Price IDs do not cross environments. Then put the live ID
in `/var/www/shop-appforgelabs-v2/apps/backend/.env` on the VPS and restart the
backend (`pm2 restart shop-appforgelabs-backend`).

### 2. Upload the vsix to R2

The product points at the key `products/lucid-reader/lucid-reader-latest.vsix`.
The name has no version in it on purpose: overwrite the same object on every
release and you never have to change code or redeploy to ship a new build.

```bash
aws s3 cp ~/dev/lucid-reader/lucid-reader.vsix \
  s3://$R2_BUCKET_NAME/products/lucid-reader/lucid-reader-latest.vsix \
  --endpoint-url https://$R2_ACCOUNT_ID.r2.cloudflarestorage.com
```

The Cloudflare dashboard upload does the same job. Afterwards, verify both the
file and the price with the health check that already exists:

```bash
bun run check:products
```

### 3. Test the whole flow locally

```bash
bun dev:db:up
bun dev
cd apps/backend && bun run stripe:webhook   # separate terminal, forwards Stripe events
```

Open <http://localhost:4321/products/tools/lucid-reader> and walk through it:

1. Signed out, the button reads "Sign in to download" and sends you to Google.
2. Signed in, "Download free" calls `POST /api/shop/claim`, the button turns
   into "Download", and the file arrives. The claim writes the ownership row
   before it answers, so the button flips without a reload.
3. The confirmation email arrives through Resend, the same one a purchase sends.
4. "Leave a tip ($5 suggested)" opens Stripe Checkout with an editable amount.
   Pay with `4242 4242 4242 4242`, any future expiry, any CVC.
5. `/purchases` lists Lucid Reader with a Download button and the tip without
   one, because a donation has no file behind it.
6. Claiming twice does nothing the second time, which is what
   `alreadyOwned: true` in the response means.

### 4. Deploy

Push to `main`. The workflow type-checks, builds, and deploys. Confirm the
backend came up (`pm2 logs shop-appforgelabs-backend`), then load the live
product page and repeat step 3 items 1 and 2 with a real account.

### 5. Connect the two listings

Once both are live, the loop closes on its own: the Marketplace listing shows a
Sponsor button pointing at the shop page, and the shop page's description points
at the Marketplace. Check that the sponsor URL resolves, because a 404 there is
the one broken link a visitor is guaranteed to click.

## Decisions I made that are yours to overrule

1. **Publisher ID `appforgelabs`.** Permanent once registered. The alternative
   is your own name, which reads as a personal project rather than a shop
   product.
2. **A new `tools` category** rather than filing an editor extension under
   `libraries`. It adds `/products/tools/` to the storefront, currently holding
   one product.
3. **The free download requires signing in.** It costs no extra code, because
   the download route already gates on ownership, and it puts an email address
   on every download. Anonymous downloads would need a new public route and
   would give up both.
4. **The donation is a separate hidden product**, not a checkout flag. This is
   what kept the change small: checkout, the webhook, the ledger, and the email
   all treat it as an ordinary purchase.
5. **The tip button says "Leave a tip", the note says it buys nothing extra.**
   Wording is in `free-download-button.vue`.

## Things I found and did not fix

**One test fails and it predates this work.**
`src/modules/auth/modes/sessions/sessions.handler.test.ts` expects
`handleGoogleSignIn` to call `res.redirect` with the Google URL, and the handler
does not call it at all any more. The redirect stored in the session is still
correct, so this is either a stale test or a real regression in the sign-in
redirect, and it needs your judgment about which. Six other tests in
`downloads.controller.test.ts` were also failing before today, for a plainer
reason: they read the live catalog and referred to `astro-vue-template`, a
product that has since been deleted. That suite now mocks the catalog and
passes.

**Two checkout paths exist and only one is used.** The storefront posts to
`/payments/stripe/checkout` (`providers/stripe/stripe.controller.ts`), while
`shop.router.ts` also exposes `POST /shop/checkout`
(`checkout.controller.ts`), which nothing in the frontend calls. They differ:
the unused one rejects a product whose `status` is not `active`, the used one
does not check status at all. Worth deleting one, separately from this work.

**The kitchen sink screenshot is the weakest of the three.** It shows the
outline and front matter well but little of the reading aids. If you want a
better third image for the listing, `scripts/screenshots.mjs` takes a theme and
a source document per entry in its `SHOTS` array.
